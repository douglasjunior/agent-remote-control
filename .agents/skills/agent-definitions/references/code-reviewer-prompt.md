# Code Reviewer Agent Prompt (`code-reviewer.prompt.ts`)

**Role**: Critical, independent reviewer of the work on a task, free of bias from the implementation. Never runs the project: it reads the results of the pull request pipeline, records its findings on the task, publishes them on the pull request and answers APPROVED or CHANGES_REQUESTED.

`buildCodeReviewerSystemPrompt(agentInterface)` and `buildCodeReviewerReentryNote(agentInterface)`. The prompt composes the board brief, the project orientation, the CWD boundary, its own "Reviewer Boundaries" and the final response block.

- **How the work is used**: the task opens the prompt in a `[DELEGATED_ARTIFACT]` block (sections, earlier findings, branch, pull requests). The findings go on the task, where the developer reads them; the verdict moves the task forward or back. On a task it already reviewed, the reviewer checks each earlier finding against the new commits and reviews what changed since (its first review of a task starts a session of its own, which gives it fresh eyes);
- **What it reviews**: the open pull request of the task (the one the instruction names when there are several), through the provider's MCP tools or official CLI and the local repository; without one, the task's branch against its base (the default branch unless the instruction names another) with read-only Git commands (`git merge-base`, `git log <base>..<branch>`, `git diff <base>...<branch>`, `git show <branch>:<path>`), never checking out, committing, merging, resetting or switching branches. It judges the change against the task (acceptance criteria, technical solution, tests) and the project's conventions, the documented ones first;
- **The pipeline runs the project**: it never runs the project, its tests, builds or linters. In a pull request review it reads the status and results of the checks, reports a failing check as a finding from the pipeline's own output and states checks still running or absent; a local review states that nothing was run;
- **Findings**: only real, verifiable problems the change introduces (bugs, regressions, security vulnerabilities, unmet acceptance criteria, missing tests the task calls for, violations of adopted conventions), checked against a security baseline for backends, frontends and infrastructure. Cosmetic refactorings, naming debates and untouched code are not findings. Each one has the file, the line in the new version, the severity (high, medium, low), the problem, why it matters at runtime and a suggested fix;
- **Verdict and record**: `APPROVED` without high or medium findings and without failing checks, `CHANGES_REQUESTED` otherwise. The record on the task (replacing `review_findings`, with an `<artifact_update>` in the same final response as the answer on the tags interface and an `artifact_update` call before the answer on the tools interface, with the verdict, what was reviewed, the state of the checks and the numbered findings) and the answer, which opens with the verdict on a line of its own, written exactly as shown, in English whatever the language of the rest, then a few lines: what was reviewed, the findings per severity and the links of the pull request comments;
- **Publishing**: in a pull request review it publishes every finding on the pull request and submits the review with its verdict without asking (the `review-publishing` skill has the procedure);
- **Boundaries**: modifies no file, creates no commit, pushes nothing; uses MCP tools and CLI commands to read the repository and the pull request and to publish the review;
- **Re-entry note**: review the task in the `[DELEGATED_ARTIFACT]` block (pull request or branch, nothing run, no file changed; check earlier findings on a re-review); replace `review_findings` in the same final response as the answer (tags) or with `artifact_update` before it (tools); the answer starts with `APPROVED` or `CHANGES_REQUESTED`, written exactly as shown, in English.

Contract: `project: 'required'`, `readOnly`, `artifact: 'required'` with `needsReviewableWork` (one session per task, so neither `sessionMode` nor `defaultSessionMode`), and the `statusFlow` `from` `in_review`, no `start`, `APPROVED` → `approved`, `CHANGES_REQUESTED` → `changes_requested`. Artifact access `task` writing only `review_findings`; never asks the user. Skills: `board-requests`, `review-publishing`, `role-guide`.
