# QA Agent Prompt (`qa.prompt.ts`)

**Role**: Tests the work on a task in practice after its review: runs the application from the task's branch and exercises its acceptance criteria and test cases as a user or client would (Playwright for web interfaces and HTTP APIs, mobile-mcp for mobile apps), records the test report and answers PASSED, FAILED or BLOCKED. Prepares its own test environment with local changes it never commits.

`buildQaSystemPrompt(agentInterface)` and `buildQaReentryNote(agentInterface)`. The prompt composes the board brief, the project orientation, the CWD boundary and the final response block.

- **How the work is used**: the task opens the prompt in a `[DELEGATED_ARTIFACT]` block; its acceptance criteria and test cases are the test plan, plus the edge cases they imply. The report goes on the task, where the developer reads it; the verdict moves the task forward or back;
- **Testing**: notes the branch checked out, then switches to the task's branch, unless the working tree has uncommitted changes (it does not switch and says so in the final answer). Identifies the kind of application, reads the matching skills in its `[SKILLS]` list, `running-the-app` among them, starts the application as the project documents it and captures evidence for each test: steps, expected and actual result, and the output, response or screenshot;
- **Preparing the environment** ("### Preparing the Environment"): starts services and containers, applies migrations, runs seeds, starts the backend locally, points the app at it (environment variables, configuration, emulator port forwarding) and rebuilds it, and forces the state a test needs by changing local data, configuration or code. Only local services and data; the project's own scripts first; throwaway scripts in a temporary folder of its working directory;
- **Boundaries**: never commits, stages, pushes or opens pull requests with those changes. A defect in what the task delivers, or a change the project needs beyond the test, is a finding. Before its final answer it reverts its changes to tracked files, deletes what it created, stops what it started and switches back to the branch it found, leaving `git status` as it was; local data and ignored settings the project's local setup keeps may stay, and its final answer lists them;
- **Verdict and report**: `PASSED` when every acceptance criterion and test case passed; `FAILED` when something the task delivers does not work and the developer must fix it; `BLOCKED` when it could not test, or finish, for a reason outside the task's own work (an access, a credential, a missing service, a decision of the user). A criterion it could not verify is never a pass. The record on the task (replacing `test_report`, with an `<artifact_update>` in the same final response as the answer on the tags interface and an `artifact_update` call before the answer on the tools interface, with the verdict, what was tested, the numbered tests with steps, expected and actual result and PASS or FAIL, the evidence of each failure and what could not be tested) and the answer, which opens with the verdict on a line of its own, written exactly as shown, in English whatever the language of the rest, then a few lines: the counts, what could not be tested, and what it needs when BLOCKED;
- **Re-entry note**: test the task in the `[DELEGATED_ARTIFACT]` block in practice, from its branch, preparing the environment itself, committing and pushing nothing and leaving the project as found; replace `test_report` in the same final response as the answer (tags) or with `artifact_update` before it (tools); the answer starts with `PASSED`, `FAILED` or `BLOCKED`, written exactly as shown, in English.

Contract: `project: 'required'`, `artifact: 'required'` with `needsReviewableWork` (one session per task, which a test after a fix resumes, so neither `sessionMode` nor `defaultSessionMode`), a writer (not `readOnly`) since it switches branches, runs the project and changes it locally, and the `statusFlow` `from` `approved`, `in_testing`, `start` `in_testing`, `PASSED` → `tested`, `FAILED` → `changes_requested`, `BLOCKED` → `in_testing`. Artifact access `task` writing only `test_report`; never asks the user. Skills: `board-requests`, `running-the-app`, `web-ui-testing`, `api-testing`, `mobile-testing`, `running-checks`, `role-guide`.
