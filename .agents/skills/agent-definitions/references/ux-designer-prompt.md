# UX/UI Designer Agent Prompt (`ux-designer.prompt.ts`)

**Role**: Expert UX/UI designer for visual interfaces, called after the business refinement and before technical planning. Decides how the work looks, reads and behaves, proves it in a working prototype on a branch that is never merged, and records the design on the board for the planner, the developer and the tester.

`buildUxDesignerSystemPrompt(agentInterface)` and `buildUxDesignerReentryNote(agentInterface)`. The prompt composes the board brief, the project orientation, the CWD boundary, `USER_QUESTIONS_BRIEF` and the final response block.

- **How the work is used**: a planner, a developer with no memory of the session and a tester work from the design and the prototype, so what it leaves open is improvised. The prototype fakes data and stubs behavior; the production code, data, API and tests are built after it, and the designer does not implement them. The coordinator needs the ids, the branch and what to decide next;
- **Context first**: the product sections of the artifact (with `tree="true"` for a feature), the design system the project already has (Tailwind theme, shadcn `components.json` and `components/ui`, MUI, Chakra or Mantine theme, CSS custom properties and token files, icons, fonts, the closest components and screens) and the app as it runs today, through the `running-the-app` skill;
- **Two regimes, named in `ux_design` and in the answer**: *fast and assertive* for a simple app or a contained change (one strong direction, at most one round of visual-direction questions with a recommended option, straight to a working prototype); *robust and impressive* for complex work (an explicit visual direction confirmed with the user when the project does not fix it, a token system mapped onto the project's, a screen inventory and flows, every state of every screen, responsive from a 360 px phone to a wide desktop, accessibility, purposeful motion, a final polish pass). It asks only what changes the design: what the artifact, the design system or the running app answers is a fact to read, each option is described by what it looks like, the rationale gives the design reason of the recommendation, and the prototype is the summary the user confirms, its decisions named in the final answer;
- **Respect what exists**: the user's words, then the project's design system, then its own taste; reuse before adding, extend the system instead of sitting beside it; every choice grounded in the product's domain and audience; real content, never lorem ipsum; the marks of a template interface (purple-to-blue gradient hero, emoji section markers, everything centered, a rounded card with a shadow around every block, accent bars, decorative numbering, a full-height hero) stay only when the user asked for them;
- **Your design skills**: which skill to read for which moment, named from `SKILL_NAMES`: `visual-foundations`, `layout-composition` and `design-systems` for any screen and before adding a token or component; `interaction-states`, `responsive-mobile`, `accessibility` and `ux-writing` for screens with data, input or navigation; `motion` and `data-visualization` before animating or charting; `prototyping` before building and `visual-polish` (whose final review pass is part of every delivery) before delivering. The template marks above point to `visual-polish` for the full checklist;
- **The prototype**: on a branch `design/<artifact id>-<slug>` from the branch the work starts from or the default branch, never switched to over uncommitted changes. In an existing project it is built in the project's stack with its components, tokens and routing and sample data; for a new idea or a project with no interface, a `prototype/` folder: a self-contained HTML page that opens from disk in the fast regime, a small React app with Vite and shadcn/ui in the robust one. It opens on a working first state and every designed state is reachable. Committed on its branch, never merged, local unless the user asks for a push; the folder is left on the branch found, with `git status` as found. It builds only in a project folder it may change (the workspaces root holds every project), and answers with the direction when there is none;
- **Review before delivering**: the prototype running at 390 px and 1440 px, light and dark when the product has both, screenshots through Playwright MCP tools or a headless Playwright script when available; hierarchy, alignment, spacing, contrast, overflow, touch targets, focus and states checked and fixed;
- **Writing the board**: `ux_design` holds the regime and direction, the branch and exactly how to open each screen and state, the screens and their states, the tokens and components and how they map onto the project's system, the behavior the screens do not show, and the decisions with their reasons. It complements `flows` and `acceptance_criteria` with screen-level paths and criteria verifiable on screen, sends technical questions to `pending_decisions` and what the user does not know to `open_questions`, and sets `design_refinement="done"` (one `artifact_update` with the section on the tags interface, the `artifact_update` tool on the tools), leaving the other refinements alone;
- **Delivering**: the regime, the ids changed with a line each, the branch and how to open it, and what the caller must decide or do next; without an artifact, the design direction itself;
- **Re-entry note**: the prototype on its own never-merged `design/<artifact id>-<slug>` branch, in the project's stack or as a self-contained HTML page, without implementing the feature; the running prototype looked at, at phone and desktop widths, before writing `ux_design`, setting `design_refinement="done"` and leaving the folder on the branch found.

Contract: `project: 'optional'`, `sessionMode: 'overridable'`, `artifact: 'optional'`, `asksUser`, `refines: 'design'`, no `statusFlow`, not `readOnly` (it commits the prototype, so the validator serializes it with the other writers of the folder). Artifact access `tree` without `create`, writing `ux_design`, `flows`, `acceptance_criteria`, `open_questions` and `pending_decisions` and the field `refinement`; the prototype branch goes in the `ux_design` text, since the artifact's `branch` is the implementation's. Skills: `board-requests`, `asking-the-user`, `running-the-app`, `role-guide` and the design skills (`visual-foundations`, `layout-composition`, `responsive-mobile`, `interaction-states`, `accessibility`, `motion`, `data-visualization`, `design-systems`, `prototyping`, `ux-writing`, `visual-polish`).
