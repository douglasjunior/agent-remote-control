# Turn Execution

How a turn runs step by step: the directory hierarchy, the tag protocol, the CEO rounds, the delegations and each agent round. Read before changing how a turn, a delegation or an agent round runs.

## Directory Hierarchy

The CEO operates at the workspaces root (`IWorkspacePort.getBaseDirectory()`, default
`./workspaces/` or `WORKSPACE_DIR`), which the channel sends as `TurnRequest.workspacePath`.
Each delegated agent operates in `IWorkspacePort.resolveRepositoryPath(project)`:

```text
./workspaces/                    ← cwd of the CEO and of GIT_OPS without a project folder
├── workspace-manifest.json      ← URL-to-folder mapping, written only by GIT_OPS
├── my-backend/                  ← cwd of the delegated agent with <delegate role="ROLE" project="my-backend"> and of one with a task of my-backend
└── my-frontend/
```

A delegation with a task runs in the task's project folder, in which the agent may work in the git repositories nested in it (`repositories/api`): the task is one project, and each of its pull requests names its repository. A delegation with a feature runs at the workspaces root, whatever the number of its projects; see "Feature scope".

### Feature scope

The agent of a feature reads the whole workspaces root and changes files only in the projects of the feature (`Artifact.projectNames`). The folders are written in the delegation, not in the system prompt, so the system prompt (and its fingerprint) is the same for every feature: `buildFeatureScopePrompt` (`prompts/feature-scope.prompt.ts`) says `You work from the workspace root and may read all of it; you may change files only in these project folders: a, b.` (`this project folder: a` for one). It follows `You hold F-1 while you work on it.` in the `[DELEGATED_ARTIFACT]` block, and opens the artifact context (`Your artifact as it stands now:`) of an `[INSTRUCTION_UPDATE]` or `[FOLLOW_UP]` for a feature, both read from the board when they are written, so the folders are the feature's projects as they stand then, whichever they were when its session started. The `<delegate>` of a feature takes no `project`: the validator refuses it, naming the projects of the feature, and refuses a feature with a project folder missing from the workspaces root. The system prompt's working directory boundary (`CWD_BOUNDARY_INSTRUCTIONS`) still holds: the root is the CWD of that agent.

Before each `createSession(cwd)`, the orchestrator calls `IWorkspacePort.ensureDirectory(cwd)`, because
`agy` fails to start in a nonexistent directory. `resolveRepositoryPath` and `ensureDirectory` reject
paths outside the workspaces root, since the project name comes from the CEO's response, and
`resolveRepositoryPath` also rejects nested paths (`my-app/src`). A project folder
must also appear in `listProjectFolders()` (direct non-hidden subfolders, including links to directories): a wrong name
would become an empty CWD created by `ensureDirectory`, so the delegation becomes `invalid` and the repair
lists the existing folders.

`IWorkspacePort` exposes `getBaseDirectory`, `resolveRepositoryPath`, `ensureDirectory` and
`listProjectFolders`: the app resolves, lists and creates directories, writes nothing else in the workspace (the
CEO's guidance is its prompt and its skills, read on demand) and does not run Git. Cloning a repository into the workspace, registering it in the manifest
and other standalone Git operations against a remote belong to the `GIT_OPS` agent, and the URL reaches it
through the specification the CEO writes. The project's own scripts that clone sub-repositories, such as an
`init`, are run by the `DEVELOPER`.

## Tag Protocol

| CEO response | Orchestrator action |
|---|---|
| With `<delegate>` | Hands the `message` to `onInterimMessage` and, for each tag, creates a new `IAgentPort` for `ROLE` with `cwd` in the project, resumes the role's session for the `artifact`, or starts another in its place for `session="new"` (without an artifact, resumes or starts the project's session according to `session` / `defaultSessionMode`) and sends `taskSpec` (prefixed with `systemPrompt(ROLE)` when the session is created) |
| With `<question>` | Queues the questions and, with the answers, runs a new CEO round in the same turn |
| Without `<delegate>` or `<question>` | Ends the loop and returns the `message` as `response`, with the resolved attachments, unless the board check below sends the CEO back first |
| *(invalid)* | Sends the repair prompt with the reason to the CEO |
| With agent requests (`<artifact_list>`, `<artifact_read>`, `<artifact_create>`, `<artifact_update>`, `<artifact_comment>`, `<skill_read>`, `<skill_list>`, `<skill_write>`) | Runs them first. With an outcome in the rest, or with only successful updates, comments and skill writes next to the text of an answer, the rest is classified and the results open the agent's next prompt; otherwise (a read, a creation, a failure, nothing but requests) `<request_results>` go back to the same agent, CEO or delegate, with a note saying why the response was not its final answer and asking for the whole final answer again, opened the way its instructions say, until a response carries none |

The classified response is the content of the `<final_response>` envelope, read by `AgentProtocolService`
(`services/agent-protocol.service.ts`), and that is why the tags go inside it. The repair prompt reinforces this rule.

The delegated agent's result returns to the CEO as `<agent_result role="ROLE" project="folder" artifact="T-1" verdict="DONE" artifact_status="in_review">\n<response>\n</agent_result>` (`project` is the project folder the agent ran in, so it is absent for a feature, whose agent runs at the workspaces root, and `artifact` absent when there is none; `verdict` is the verdict the final answer opened with, absent without one; `artifact_status` is the artifact's status read after the verdict was applied, followed by `artifact_status_by="user"` when a user set it while the agent worked). A response whose verdict closed the step (`DelegationStatusService.finish` reports `closesStep`: its status differs from the one the delegation worked in) is a receipt: longer than `AGENT_RESULT_MAX_CHARS` (`DelegationLimitsConfigService`, default 2000, `0` disables the cut), its body is cut at the limit and closed by `[The rest of this result, N characters, was left out. The full report is on T-1, in its <section> section.]`, naming the sections of the role's `ArtifactAccess` (the artifact alone when it has none). A verdict that keeps the task where it was (`INCOMPLETE`, `BLOCKED`) carries the decision and its options, or what the agent needs, only in the answer, so it goes whole, and so does a response without a verdict (an access request, a decision for the user, a key to relay). The `finished` delegation event always carries the whole response for the channel. A result with `status="stopped"` comes from `ActiveDelegation.stop(reason)`: `StopArtifactWorkUseCase` listens to the board (`IArtifactsPort.onChange`) and, when a user moves a held artifact to a work-ending status, stops the delegation holding it (`delegationId`). The stop discards the agent's pending questions and cancels its turn without ending the CEO's: the reason (`buildStoppedWorkPrompt`: who stopped it, and that what the agent changed in its project, or in each project of its feature, stays there for the user to keep or discard) becomes the result body and the turn goes on. In a parallel delegation, the results arrive together, one block per delegation, in tag order, separated by a blank line.

## Turn Execution

A turn is split by responsibility:

- `ExecuteAgentTurnUseCase` runs the CEO turn: steering, the CEO rounds, repairs, the CEO's questions, resumed work and the `TurnResult`.
- `DelegationValidatorService.decide(response, request, userInitiated)` classifies a CEO response and checks every delegation in it.
- `RunDelegationUseCase` runs the delegated agents (`start`, `stopRunning`) and turns each one into an `<agent_result>` (`prompts/agent-result.prompt.ts`).
- `AgentRoundService.run(input)` sends one prompt to one agent, CEO or delegate, in its session, with its profile; it also resolves the conversation's session, the role's agent, its `agentInfo` and the language block.
- `AnswerAgentQuestionsUseCase` carries an agent's questions to the user and the answers back (`buildUserAnswersPrompt`).
- `RunAgentRequestsUseCase.resolve` carries out the board and skill requests of each response before it is classified.
- `TeamProfilesService.build` writes the `[TEAM_PROFILES]` block, and `CeoBoardService.buildPrompt` the `[BOARD]` block.
- `DelegationStatusService` moves the status of a delegated task: `refusal`, `start` and `finish`.

Running `ExecuteAgentTurnUseCase.execute(request: TurnRequest): Promise<TurnResult>` follows this sequence:

1. **Turn lifecycle**: after transcribing the audio, `ConversationRuntimeService.admit(conversationKey)` either starts the turn, ended in `finally` by `endTurn`, or joins the running one (see "Messages During a Turn" in the skill): the message goes into the turn's inbox, its record is added to the root's open work, and, while a CEO prompt is on its way on an agent that takes steering, the inbox is steered into it; the call then resolves as `steered` once the CEO read it, `cancelled`, or runs the next turn when the message is handed it.
2. **Turn agent**: each role resolves its agent from the conversation's `AgentSettings` through `resolveProfile`, falling back to `IAgentPortFactory.defaultAgentId`, which is read only when no profile exists because it scans PATH. The CEO port uses the CEO profile; each delegate uses its own role's profile, read when the delegation starts. The settings are read at every turn and delegation start, so a saved change applies to the next one without interrupting work in progress.
   - **Steering**: `steerCeo` with a `buildUserMessagePrompt` block per message (`prompts/user-message.prompt.ts`, a `[USER_MESSAGE]` block that tells it to continue the current task taking the message into account, because without it the model tends to answer only the message and end the round) over the text enriched with `[ATTACHMENTS]`, preceded by the `[TEAM_PROFILES]` and `[BOARD]` blocks and the pending receipts; a live session gets no re-entry note. A steered message resolves as `status: 'steered'` with the CEO's `agentInfo`. One not steered (agent without steering, CEO connecting or between prompts) waits in the inbox for the next CEO prompt of the turn. A steering the agent does not take, or that throws (logged as `[CEO Steering Failed]`), puts its messages back in the inbox, unless the user stopped the turn meanwhile, which cancels them.
3. **CEO rounds**: runs each CEO round via `ConversationRuntimeService.runOnCeo(conversationKey, turn, ...)`. Every prompt of the round takes the inbox first and appends a `[USER_MESSAGE]` block per message (`delivered`), marking the round user-initiated; while specialists work in the background, a new message wakes the CEO for a round of its own.
4. **Session resolution and prompt enrichment**: resolved in the CEO's first round inside `runOnCeo`. If there are `request.attachments`, it enriches the prompt with the `[ATTACHMENTS]` block detailing the local inventory (name, size, MIME type and absolute path on disk) and instructing the agent to inspect the files using the tools available in its environment. It injects the `[TEAM_PROFILES]` block (`TeamProfilesService.build`) into the CEO's initial prompt: one line per role of `IAgentRegistryPort.listRoles()` except the CEO's, with the coding agent, model and effort, and `Status: idle` or `Status: working`. The profile comes from the conversation settings (`resolveProfile`, falling back to the CEO's profile, then to the default agent and `default` for model and effort); a working role shows the `agentInfo` it started with (`ActiveDelegation.agentInfo`, resolved with `AgentRoundService.buildAgentInfo` when the delegation starts, so a settings change applies to the next delegation and not to the running one) plus `Running` time, `Project`, `Artifact` (when it holds one), `Waiting for user` (`UserQuestionQueueService.isWaiting`) and the `Summary` of the task (`ActiveDelegation.summary`, the `summary` attribute of the `<delegate>`). The block is always present, so the CEO reads a prompt without it as an unchanged team, and a CEO session that was just created or switched has no memory of who is on the team. In later rounds of the same turn the block is sent again only when its signature (profiles, states, projects, wait states and summaries, without elapsed time) changed since the last block of the turn. The `[BOARD]` block (`buildBoardPrompt(ArtifactPromptFormatterService.digest(all))`, `No open artifact.` on an empty board) follows it in the first round of every turn and in no later round, since each `<agent_result>` carries the status it left. The digest has a compact line per open feature (id, type, title, status, project) and per task under way (id, type, title, status, its feature or, standing alone, its project, `with` the holder, `waiting on` the open dependencies, the count of `pull requests`), then the `Ready:` tasks by feature and the `Backlog:` tasks with the refinement each owes. Notices pending from a turn that failed or was cancelled come before it in a `[PREVIOUS_TURN]` block (`buildPreviousTurnPrompt`): how the turn ended, each agent stopped before finishing (a delegation the CEO replaced is left out) and each delegation the round limit kept from starting. `ConversationRuntimeService` holds them in memory, outside the runtime that expires when idle, and they leave once a CEO round returns; a restart loses them.
5. **Delegation loop**: runs one CEO round per prompt; `MAX_DELEGATION_ROUNDS` (1000) bounds the rounds in which the CEO delegates, a last resort that also covers delegations without an artifact; the guard against agents looping on a task is the freeze of the artifact after too many delegations:
   1. Runs the CEO turn with `cwd = request.workspacePath`, through `RetryCeoRoundUseCase`: every prompt sent to the CEO that throws, and a response that is still `invalid` after the repair below, shows the failure with `onRetry`, waits (`TurnRetryService`) inside the same `ActiveTurn` and sends that prompt again with `buildTurnRetryPrompt`; the turn fails only once the user ends the retries or their time (`TURN_RETRY_MAX_TOTAL_MS`) is spent.
   2. Classifies the response with `DelegationValidatorService.decide()`, which detects the outcome with `DelegationDetectorService.detect()` and validates each delegation: the role must exist (`hasRole`) and differ from the root role, a role whose contract has `userInitiatedOnly` is accepted only when `userInitiated` (the round answers the user's message or `<user_answers>`, not an `<agent_result>`), the tag attributes must fit `getDelegationContract(role)`, an `artifact` must pass the board checks (see "Artifacts"), which also set the delegation's scope (a task's project becomes its `project`; a feature takes no `project`, runs at the workspaces root and needs each of its projects in `listProjectFolders()`): after the frozen and closed checks, a task in a status the role's `statusFlow` does not take is refused with `DelegationStatusService.refusal` (naming the refinement still owed and the roles that settle it, for a `backlog` task), and a specification longer than `DELEGATION_SPEC_MAX_CHARS` (default 600, `0` disables the limit; no limit without an artifact, nor for a delegation to a role whose running agent already works on that artifact, which receives the new text alone) is refused with `The specification of <id> has N characters, and the limit with an artifact is M. The agent receives <id> in full (its sections, branch, pull requests and comments), so say only what to do with it now. A fact the task lacks goes on it as an <artifact_comment> in the same response. Do not restate its sections.`; and the project must be accepted by `resolveRepositoryPath` and appear in `listProjectFolders()`. A delegation to a role with an active delegation needs `on_busy` unless it is on the same work (same project and artifact) of an agent `SteeringSupportService` knows to take steering; without it the repair is `buildBusyRoleRepair` (the agent's work, why, and what `wait` and `interrupt` each cost). Validation failures become `invalid`, and project failures list the existing folders in the reason. With several delegations, it validates each one and then the set: the same role does not appear twice, whatever the project, nor the same artifact, and at most one agent that modifies files works in each project folder, counting active delegations from previous turns (`occupiedFolders`: a task's agent occupies its project, a feature's agent every project of the feature as the board lists them now, and an agent with neither the workspaces root, which is a folder of its own); agents with `readOnly` in the contract do not count. A delegation never conflicts with the active delegation of its own role, since it goes to that agent or runs after or in place of its work, never beside it; that agent's folders still count against the other roles until it ends, `on_busy="interrupt"` included, since the other delegations of the response start while it stops.
   3. **Repair**: on `invalid`, sends `buildDelegationRepairPrompt(reason)` (`prompts/delegation-repair.prompt.ts`), starting with `[DELEGATION_ERROR]`, to the CEO and classifies the new response. There are up to `MAX_REPAIR_ATTEMPTS` (1) attempts per CEO response, outside the round count. If it remains `invalid`, returns `status: 'failed'` with `errorMessage: 'Invalid CEO response: <reason>'`.
   4. `ask` does not leave the round: the CEO waits for the answers in the queue and receives `<user_answers>` on the same port, inside `runOnCeo`, with `isUserMessage` true (the system prompt accompanies it); the new response is classified and repaired like the first. `reply` ends with `status: 'completed'` once no delegation of the turn is running; while some still run, its text goes to `onInterimMessage` and the loop keeps waiting for their results.
      **Board check**: the first `reply` with nothing running is checked against the board (`CeoBoardService.findStranded`) for the tasks the turn started delegations for (restored work included), which the turn loop collects: those in `ACTIVE_TASK_STATUSES` that no agent holds and whose id the answer does not name, as a whole id. With any, the answer is not delivered, attachments included: the draft is cleared (`onDraft('')`), `[Board Check]` is logged and the CEO gets `buildBoardCheckPrompt(tasks)` (`[BOARD_CHECK]`, after the results of the answer's board writes), which says the answer was not delivered and that the answer ending the turn, after routing or instead of it, must be complete with every attachment; its response is handled like any other, and the turn is checked once, so a second answer is final. Only the work of the turn counts: a task parked in an earlier turn, or a turn that delegated no task, never triggers the check.
   5. On `delegate` in the last allowed delegation round, it ends without running the delegate (item 6), because the result would not return to the CEO.
   6. In the other rounds, on `delegate`, it hands the non-empty `message` to `onInterimMessage` and starts all delegations in parallel (`RunDelegationUseCase.start`), each as below, tracked in `RunningDelegations` (`models/running-delegations.model.ts`). The next CEO prompt is built from the results as the agents finish: `nextResults(turn.arrival())` waits for the first one, or for a user message, and returns every result finished so far (an empty text when woken first, or when every agent left was replaced or took the work into another run), so results that finish while the CEO is busy arrive together. If one was cancelled, the turn is cancelled. A delegation that failed with another error becomes the block `<agent_result role="ROLE" project="folder" status="failed">\n<message>\n</agent_result>` (logged as `[Delegation Failed]`), delivered like any other result so the CEO decides between retrying the task or notifying the user. When the turn ends with delegations still running (invalid CEO response, failure, cancellation), `RunDelegationUseCase.stopRunning` discards their questions from the queue, because a wait for an answer would hold the turn open until the user answered, cancels the ones still pending and waits for them to settle, so no agent keeps running unobserved. It touches only what the turn itself started (each `StartedDelegation` carries its `cancel`, `RunningDelegations.cancelPending`): an agent it is waiting for is cancelled, a follow-up it queued is taken back (or, once running, cancels the agent), and a delegation waiting for another agent stops waiting. A delegation that has just stopped waiting, or is still opening, does not start: `start` remembers the stop per delegation, `open` checks it before and after assigning the artifact and releases the artifact as cancelled, and from the registration on the stop cancels the delegation's own turn:
      - When the role already has an active delegation, in any project (`findActiveDelegation`), the delegation reaches that agent as described in "Agents Already at Work" of the skill, under a lock per conversation and role (`RunDelegationUseCase.exclusive`) that also covers starting a delegation up to its registration:
        - **Steered**: same work without `on_busy`: `sendSteeringPrompt` with `buildInstructionUpdatePrompt([text], changes on its task since `control.contextSince`)` and the language block. `injected` delivers it; any other outcome keeps it (`DelegationControl.keep`) for the next prompt of the run, which `withInstructions` appends when the prompt is written; after the final response, `seal` either ends the run or, with an instruction still kept, sends an empty prompt that carries it. No prompt is lost or restarted, and an agent waiting for the user's answers gets it with them.
        - **Interrupted, same work**: `keep(instruction, true)` and, in the same tick, `IAgentPort.cancel` (or `UserQuestionQueueService.discard` for an agent waiting for answers). `runPrompts` catches the cancellation when `takeInterruption()` says it came from the instruction and the delegation's own turn is not cancelled, and sends the next prompt, in the same session, with the instruction.
        - **Follow-up**: `wait` on the same work, or a steering or interruption the run does not take because it is finishing (`acceptsInstructions` false): `DelegationControl.follow` queues it; after the current run, `drive` settles that run's result at once and runs the follow-up on the same port as a run of its own (`buildFollowUpPrompt`, its own event id, status `start`/`finish`, result to the turn that sent it). A follow-up whose turn ends before it ran is withdrawn; follow-ups a failed, stopped or replaced delegation never ran become failed results (`buildUnrunFollowUpPrompt`), and a cancelled one takes them along.
        - **Waiting**: `wait` on other work, or any instruction for a delegation already closing: `waitForEnd` counts it as a waiter (shown as `Queued` in `[TEAM_PROFILES]`) until `control.ended`, then decides again; a cancelled agent cancels the delegations waiting for it.
        - **Replaced**: `interrupt` on other work: marks the agent as replaced, discards its questions, cancels its turn and awaits `control.ended`, which resolves once its delegation released its artifact and closed its agent, then starts the new delegation. The replaced run emits `cancelled` and its outcome is `replaced`: it gives its turn no result. A delegation that took its instructions into a run already under way (outcome `merged`) gives no result of its own: the CEO hears from that run.
        - Each instruction steered, kept or interrupting is recorded (`control.record`: the new `summary`, appended to the updates of the open work), emits `onDelegation` `steered` with the run's event id, and leaves a receipt in `ConversationRuntimeService.addAgentReceipt` (`<agent_result status="steered|queued|interrupted">`, the old work's artifact and status for a replaced one); so does queueing a follow-up or a waiting delegation. The CEO gets the receipts before the body of its next round prompt, or in a steered user message: each prompt takes the receipts it carries, so each reaches the CEO once, and one that fails gives them back for the next. The retry of a prompt carries again the receipts steered into it (`ConversationTurn.markSteeredReceipts`/`takeSteeredReceipts`), as it does the steered messages.
      - Creates the delegate's port with `create(agentId)`, creates `ActiveDelegation` (with its `DelegationControl`) and registers it in the runtime before the role's lock is released.
      - **Session and opening prompt**: a delegation with an artifact runs with `artifactId` and its `session` attribute, `resume` when it has none, so it resumes the role's session for that task when there is one and creates one otherwise; `session="new"` (accepted for a role whose contract has `sessionMode`, rejected for another) skips the stored session and creates one whose binding replaces the task's, so the next delegations of the task resume it, and it receives the whole task like any new session. The role's `defaultSessionMode` applies only without an artifact. Without an artifact, `session` or `getDefaultSessionMode(role)` chooses between the role's session in the project and a new one. The first prompt is an `AgentPrompt` function that `AgentRoundService.run` calls once it knows the session state (`openingPrompt`). With an artifact, it opens with `[DELEGATED_ARTIFACT]\nYou hold <id> while you work on it.`, for a feature the scope line ("Feature scope"), then the content and `[/DELEGATED_ARTIFACT]`, then the task: a new session (first time on the task, a failed `session/load`, another coding agent, a stored session still `unanswered`) gets the full content (`ArtifactPromptFormatterService.detail`); a resumed one on a task whose binding records `workEndedAt` gets `changesSince(artifact, all, workEndedAt)`: `# <id> · <title>`, the status, dependencies, refinement states, holder, branch and pull requests, a sentence saying everything else is unchanged since the agent last worked on it (or that nothing besides those facts changed), and the sections changed (`section:<name>` history changes) and comments added from that moment on, that moment included. The moment belongs to the session, not the role: a role that worked on the task through another coding agent meanwhile left changes this session has not seen. A resumed session whose binding records no end of work, and any feature (what changed in its tasks is not in its own history), get the full content. Restored work and delivered answers (`firstPrompt`) send that prompt alone in a resumed session, which was holding the task when it stopped, and the full content before it in a new one.
      - **Status of the task**: with an artifact, `DelegationStatusService.start` runs once the artifact is assigned and returns the status the delegation works in: it moves the task to the role's `statusFlow.start` only from a status of `statusFlow.from` (the task already in it, as for restored work and delivered answers, stays), works in the current status for a role without a start, and returns none for a task in a status the role does not take, which it leaves alone: restored work skips the validator, and the task may have been cancelled or moved meanwhile. `finish` reads the verdict that opens the final answer and applies its status only while the task is still in that working status, before the result's artifact details are read and before the release, so a status the user, the CEO or anyone else set while the agent worked stands; it still reports the verdict, and whether it closed the step. A delegation that failed, was stopped, replaced or cancelled applies no verdict. In `finally`, after the release, `AgentRoundService.recordWorkEnded` sets `workEndedAt` on the binding of the session the port holds, whatever the outcome, when the agent answered at least one prompt of the delegation (a delegation whose prompts all failed keeps the earlier `workEndedAt`, since what it told the session is unknown); a failure is logged as `[Session Record Failed]`.
      - Logs `[Delegation Started]` and emits `onDelegation` `started`; on completion, logs `[Delegation Finished]` with the number of prompts of the delegation, their characters and, when the agent reports usage, the input, output and total tokens, and emits `finished` with `usage` added up over every prompt (`AgentRoundInput.onPrompt`); on a cancellation, emits `cancelled` before rethrowing it, and a pending notice reports the agent as stopped before finishing.
      - Between start and completion, each delegate response goes through `AnswerAgentQuestionsUseCase` (`QuestionParserService` first): with questions, it waits for the answers in the queue and returns them to the same agent, on the same port and session, until it responds without questions. Malformed markup receives one repair (`buildQuestionRepairPrompt`, starting with `[QUESTION_ERROR]`) per response, and so do the questions of a role whose `DelegationContract` lacks `asksUser` (`buildQuestionNotAllowedPrompt`: answer without questions, the decision and its options in the result); if it persists, the response goes on as the result. Only the final response becomes `<agent_result>`.
   7. When its last run ends, the delegation closes to follow-ups, closes its open work, releases its artifact, records the end of work, removes itself from the active delegations registry, shuts down the delegated agent (`closeSession()` + `disconnect()`), settles the last run's result and resolves `control.ended`.
   8. The CEO's next prompt is the pending receipts, then the `<agent_result>` blocks finished so far (each tagged `agent`, `model` and `effort` from the same `agentInfo`, `default` when unset), separated by a blank line, after the `[TEAM_PROFILES]` block when the team changed (and the `[BOARD]` block when it opens the turn, as for restored work).
6. **Round limit**: when the delegation rounds are exhausted, returns `status: 'failed'` with `errorMessage: 'Max delegation rounds exceeded.'`.

Each agent round (`AgentRoundService.run`, CEO or delegate) runs:

1. `turn.activate(agentPort)` and `turn.throwIfCancelled()`.
2. `connect()` followed by `turn.throwIfCancelled()`.
3. The session state is `live` when `currentSessionId` is set, and its tool session, if any, passes to this round's `requester` and turn (`AgentToolSessionsService.update`); otherwise (`openSession`), with the servers of a tool session opened for the round's `requester` (`AgentToolSessionsService.open`, none for an agent without `supportsHttpMcp`) sent with the load and with the creation alike:
   1. **With a session in `agentSessions` for the role, the port's agent (`agentId === agentPort.agentName`), the project and the artifact (`null` without one), and `sessionMode !== 'new'`**: rereads the `SessionContext` from the store and calls `loadSession(cwd, sessionId)`; on success the state is `resumed`. The reread is necessary because the turn's object does not reflect the sessions written by the CEO and by previous rounds.
   2. **Without an ID, `'new'` mode or a failed load**: `ensureDirectory(cwd)` and `createSession(cwd)`; the state is `new`.
   3. If the ACP session ID changed, replaces the entry of that key in `agentSessions`, preserving the others, and saves to the store. The entry of a created session carries `unanswered: true`.
   4. **A loaded session whose entry is `unanswered`, and a live one of a port whose first prompt failed**: the state is `new`, so the system prompt and the whole task go again. The first `thought` or `tool` activity of the prompt, or its end, takes the mark off the entry (`recordAnswered`; a failure is logged as `[Session Record Failed]`), so a restart in the middle of a prompt the agent was working on finds a `resumed` session.
4. The prompt, written for the interface of the session (`AgentToolSessionsService.interfaceOf`: `tools` while the port has a tool session open, `tags` otherwise), in this order: `getSystemPrompt(role, agentInterface)` and the `[SKILLS]` catalog for a `new` session (and, with `isSystemPromptEveryTurn(role)`, in the CEO's first round of each user message and in the round that delivers `<user_answers>` to the CEO, including in a resumed session; the rounds with `<agent_result>` and the repair prompts of the same message do not repeat it; and in a `resumed` session whose binding records no `promptHash`, or one other than the fingerprint of the system prompt now built with its catalog, so that a session started before a prompt or a skill changed gets the current rules, logged as `SystemPrompt=yes (changed)`); `getReentryNote(role, agentInterface)` for a `resumed` session only, since a new one has the system prompt and a live one keeps its instructions, followed by the current `[SKILLS]` catalog of the role for a `resumed` session that did not receive the system prompt (a compaction can drop the one in its transcript; a catalog that differs from the one the session was sent changes the fingerprint, so that session gets the system prompt with it instead; the CEO gets it with its system prompt); `buildLostSessionTaskPrompt` for a `new` session receiving `answerDelivery`; the prompt (an `AgentPrompt` function is called with the state); the language block. The `[SKILLS]` catalog, with the system prompt or after the re-entry note, goes when the role has skills or writes them (`buildSkillCatalogPrompt(skills, agentInterface, writesSkills)`, `prompts/skill-catalog.prompt.ts`). The catalog is the one explanation of skills every agent gets, the CEO included: the listed skills are kept by the server and read only through `<skill_read>`, or the `skill_read` tool of the `arc` server on the tools interface, in addition to the guidance and skills a project keeps in its own files, which the agent still follows; for a role that writes skills it adds listing them, reading any skill and writing one (`<skill_list/>` and `<skill_write>`, or `skill_list` and `skill_write`), pointing to the listed skill about writing skills. The system prompt accompanies the creation of the ACP session, not that of the `SessionContext`, so that a recreated session receives the role's instructions. The fingerprint is the first 16 hex characters of the SHA-256 of the system prompt text (the role's prompt followed by the catalog) and is computed for every prompt of a session that is not live; a prompt that carries the system prompt records it on the session's binding at the same first sign of the agent at work that takes off `unanswered` (`recordAnswered`), so a prompt the agent never started answering leaves the earlier one.
5. Configuration: with the role's profile for the same agent as the port and `modelId` set, `setConfig({ modelId, effortId: effortId ?? undefined })`; otherwise, `setConfig({ modelId })` when `getDefaultModel(role)` returns a model. A profile for another agent is ignored because model IDs are not valid across agents. Applies to the CEO and to delegates. Since sessions are keyed by role, agent, project and artifact (`null` project for a feature's agent, which runs at the workspaces root, so its session survives changes to the feature's projects), changing a role's agent starts a new session for it, while changing only its model or effort keeps the session.
6. Registration of a listener via `onActivity(...)`, undone in `finally`, feeding an `AgentProtocolStream` (`AgentProtocolService.stream`) per prompt. The stream relays the activities of every agent to `request.onActivity`: a message with a `<final_response>` envelope settles its `thought` entry to the prose before the envelope (`final: true`) or takes it back (`removed: true`) when there is none. It also reports the answer as it stands, whole at every change (the content of the envelopes or, while no message has one, everything the agent said, reasoning excluded, a tag being typed held back): the CEO's becomes `request.onDraft` calls and those of delegated agents are not asked for.
7. `turn.throwIfCancelled()`, the `[Agent Prompt]` log (session `live`, `resumed` or `new`, its interface, whether the system prompt goes with it: `no`, `yes`, or `yes (changed)` for a resumed session whose recorded fingerprint differs, its characters) and draining of `prompt(text)`, accumulating the text blocks as the fallback response. After every prompt of the round, the usage the port reports (`getLastRoundUsage`) is logged as `[Agent Usage]` and the prompt's characters, response characters and usage go to `onPrompt`.
8. Protocol violations in the response, checked on the agent's final message, which is the response (`AgentRoundService.run`, for the CEO and every executor alike). One repair prompt at most, sent to the same agent with the CEO's draft discarded first, and its answer is the response:
   1. **More than one `<final_response>` block** (`AgentProtocolService.finalResponseBlocks`): the blocks are not joined; the agent receives `buildFinalResponseCountRepairPrompt(count)` (`prompts/protocol-repair.prompt.ts`, starting with `[PROTOCOL_ERROR]`, saying how many blocks the response had and asking for the whole answer in a single block at the end of the turn); logged as `[Protocol Repair]`. Text after the closing tag is narration, not a violation.
   2. **Protocol tags outside the envelope**: when the text has a `<final_response>` envelope and protocol tags were written outside it, outside Markdown code (`AgentProtocolService.strayTags` over everything the agent wrote in the prompt), text that is otherwise narration:
      1. **Only artifact and skill requests**: the raw text of each (`AgentRequestParserService.parse(...).raw` of `AgentProtocolService.narration`) whose text, whitespace aside, the final response does not also carry goes, in order, in front of the final response the round returns, so the caller's `RunAgentRequestsUseCase.resolve` carries each request out once; logged as `[Stray Requests]`.
      2. **Any other tag** (`<delegate>`, `<question>`, `<attachment>`, `<user_language>`): the agent receives `buildProtocolRepairPrompt(tags)` (same file, starting with `[PROTOCOL_ERROR]` and naming the tags); logged as `[Protocol Repair]`.
9. Response: `AgentProtocolService.finalResponse` of `lastAgentMessage` or of the accumulated blocks (the content of the envelope, accepting an unclosed one, or the whole text when there is none; the envelopes of a response still with more than one after its repair are joined), logged as `[Agent Response] Role=<ROLE>, Length=<n>` with a 100-character single-line preview.

**Cancellation and failure handling**: `PromptCancelledError` (or an error with the same
name) thrown by any agent or by `ActiveTurn` returns `status: 'cancelled'`. Other
errors return `status: 'failed'` with `errorMessage` and disconnect the CEO agent, so that the
next turn starts a new transport and resumes the session. In both cases, `response` receives
the `lastAgentMessage` of the CEO port used in the turn, read by `AgentProtocolService.finalResponse` (empty when the turn fails before there is a port).

**Turn metadata**: `agentInfo.roleName` comes from `getDisplayName(role)` and `agentName` from the
CEO's `IAgentPort` (the turn's `agentId` when there is no port yet). `modelName` and `effortName`
come from the role's profile of the same agent; without them, `modelName` is the `displayName` of
`getAvailableModels().currentModelId`.
